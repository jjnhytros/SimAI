# Piano release 0.1170 — Ottimizzazione residua moodlet

**Data**: 2026-10-30
**Tipo**: ottimizzazione (tocca `run_tick`, ma comportamento invariato)
**Base**: 0.1160 (403 test verdi, `10y-0.1160.json`, tps 58.6 pre-batch / 63.3 post-batch su 1y)

## Motivazione

`known-issues.md` §17.7 documenta il residuo N+1 di 0.1160:
`update_mood` chiama `active_delta` (5 SELECT/tick) e `cleanup_expired`
fa 5 DELETE/tick. Sono query per-personaggio in un contesto dove tutti
i personaggi vengono processati ogni tick. 0.1170 le rende batch.

**Nessun cambio di comportamento.** Le funzioni batch sono
matematicamente equivalenti a quelle per-char. Il 10y non viene
rieseguito: misura il comportamento, e il comportamento non cambia.
Il `tps` post-0.1170 si misura al prossimo 10y accumulato (0.1180 o
successivo).

## Scope

1. `active_delta_many(session, char_ids, tick) -> dict[int, float]`
   in `mood/moodlets.py`: 1 SELECT invece di N.
2. `cleanup_expired_many(session, char_ids, tick) -> int` in
   `mood/moodlets.py`: 1 DELETE invece di N.
3. `update_mood`: nuova keyword `moodlet_delta: float | None = None`.
   Se passata, salta `active_delta`. Retro-compatibile.
4. `sim/tick.py` fase 3: `active_delta_many` + `update_mood(...,
   moodlet_delta=...)` + `cleanup_expired_many`.
5. 4 test: 2 per `apply_intimacy_moodlets_many` (mancanti in 0.1160),
   2 per `active_delta_many`/`cleanup_expired_many` (equivalenza
   batch vs per-char).

## Non-scope

- `apply_intimacy_moodlets_many`: già batch da 0.1160.
- `refresh_need_moodlets_many`: già batch da 0.1101.
- `active_delta` e `cleanup_expired` per-char: restano per test e
  CLI. Non si rimuovono.
- 10y: non rieseguito. Comportamento invariato.
- `Relationship.intimacy_level` persistito: no, derivato.

## Design

### `active_delta_many`

```python
def active_delta_many(
    session: Session, char_ids: list[int], tick: int
) -> dict[int, float]:
```

1 SELECT: moodlet attivi per tutti i `char_ids`, finestra
`[started_at_tick, expires_at_tick)`. Aggrega in Python per `char_id`.
Char senza moodlet: `0.0` (presente nel dict, non assente).

### `cleanup_expired_many`

1 DELETE: moodlet con `expires_at_tick <= tick` per tutti i
`char_ids`. Ritorna `rowcount`.

### `update_mood(moodlet_delta=...)`

- `moodlet_delta is not None`: usa il valore passato, salta
  `active_delta`.
- `moodlet_delta is None` e `tick is not None`: comportamento
  originale (`active_delta` per-char).
- `moodlet_delta is None` e `tick is None`: delta = 0.0.

I chiamanti esistenti (test, CLI) non cambiano. Solo `tick.py` passa
`moodlet_delta`.

### Ordine in `tick.py` fase 3

```
apply_intimacy_moodlets_many(...)
active_delta_many(...)              # legge i moodlet, incluso quello appena applicato
per ogni char: update_mood(..., moodlet_delta=deltas_by_char[cid])
cleanup_expired_many(...)           # rimuove gli scaduti DOPO update_mood
```

L'ordine non è arbitrario: `active_delta_many` deve vedere il moodlet
appena applicato da `apply_intimacy_moodlets_many`; `cleanup_expired_many`
non deve cancellare un moodlet prima che `update_mood` lo legga.

## Rischi

- (a) **`active_delta_many` e `update_mood` divergono**: il test di
  equivalenza (`test_active_delta_many_matches_per_char`) copre
  l'unico caso che conta. Se in futuro `active_delta` cambia
  finestra, il test fallisce.
- (b) **Ordine fase 3**: se `active_delta_many` è chiamato prima di
  `apply_intimacy_moodlets_many`, il moodlet appena applicato non
  contribuisce al tick corrente (un tick di ritardo). Il commento
  nel codice lo esplicita; il test `test_mood_mean_unchanged` (se
  esiste) lo coprirebbe indirettamente. Non lo aggiungo: il 10y di
  0.1160 ha già confermato `mood_mean` 70.6. Se in futuro cambia,
  si vede al prossimo 10y.
- (c) **`tps` non misurato**: atteso ~+5–8 tps (recupero di ~8
  query/tick su 10). Non verificato. Si misura al prossimo 10y.
  Documentato in `known-issues.md` §17.7.
