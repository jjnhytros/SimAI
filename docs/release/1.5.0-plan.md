# SimAI 1.5.0 — NPCManager

**Obiettivo**: introdurre `NPCManager` come astrazione sopra il loop
di tick, senza cambiare comportamento osservabile. Il tick deve
produrre gli stessi `TickDecision`, stesso ordine, stessi effetti.
Nessuna feature nuova visibile. Il valore è architetturale: creare il
posto dove la FASE 3 (lifecycle, skills, memoria, identità) potrà
agganciarsi senza riscrivere il tick ogni volta.

**Non obiettivo**: `RelationshipKind` 11 (A2), LOD (FASE 1.1), skills,
memoria, lifecycle, identità, vizi, riflessione. Nessuna feature
visibile. Nessun cambio di `tick.py` oltre alla delega.

**Dipendenze già in piedi**:

- `tick.py` con loop inline su `Character`
- `SimState` (`tick_index`, `master_seed`)
- `save`/`load` con schema versionato
- 248 test verdi, 10y di 1.4.0 come baseline

**Dipendenze non risolte (dichiarate)**:

- `NPCState` è in-memory, non persistito. Ricostruito da DB a ogni
  `load()`. Il save resta quello di oggi.
- Nessun `SkillSnapshot`. Non c'è skill. Sarà aggiunto in 3.6a-c.
- Nessun LOD. Il manager carica tutti gli NPC, non solo quelli
  vicini al player. Sarà 1.6.0 o FASE 1.1.

## Cosa entra

### 1. `NPCState` (in-memory, dataclass mutabile)

Campi minimi:

- `character_id: int`
- `key: str`
- `location_id: int`
- `home_location_id: int | None`
- `traits: list[str]`
- `balance: float`
- `needs: dict[NeedKind, float]`
- `is_player: bool`

Niente di più. Se aggiungo campi che non uso, mento su cosa serve.

### 2. `NPCManager`

- `load(session, *, include_player: bool) -> list[NPCState]`
  carica tutti gli NPC in una query, più una query per i bisogni
  per personaggio (N+1 dichiarato, vedi §6).
- `update_all(session, states, *, tick_index, master_seed) -> list[TickDecision]`
  itera su `states` in ordine di `character_id`, chiama `_tick_one`,
  ritorna la lista. L'ordinamento è esplicito: indipendente
  dall'ordine di input.
- `_tick_one(session, state, *, tick_index, master_seed) -> TickDecision`
  esegue la logica già in `tick.py` per un singolo NPC:
  priorità lavoro → priorità casa → `choose_intent` → esegui.
  Mantiene `state.location_id` e `state.balance` sincronizzati
  con il DB dopo move/acquisto.

### 3. `NPCManagerLike` Protocol

```python
class NPCManagerLike(Protocol):
    def load(self, session: Session, *, include_player: bool) -> list[NPCState]: ...
    def update_all(
        self, session: Session, states: list[NPCState], *, tick_index: int, master_seed: int
    ) -> list[TickDecision]: ...
```

`run_tick` accetta `npc_manager: NPCManagerLike | None = None`. Se
`None`, usa `NPCManager()`. Permette test di contract con un manager
finto, senza cambiare `tick.py` una seconda volta.

### 4. `TickDecision` e `TickReport` spostati in `sim/reports.py`

Necessario per evitare ciclo `tick.py → manager.py → tick.py`.
`tick.py` li re-esporta (`__all__`), nessun test esistente si rompe.

### 5. `npc/__init__.py` **vuoto**

`npc.traits` è importato da `actions.utility`. Se `npc/__init__.py`
re-esporta `NPCManager`, si innesca un ciclo `utility → npc.traits →
npc.manager → actions.intent → utility`. Il package resta vuoto:
chi vuole `NPCManager` importa da `simai.npc.manager`.

## Cosa non entra (esplicito)

- `RelationshipKind` 11 (A2)
- LOD, distanza, `lod_from_distance`
- Skills, `SkillSnapshot`, talenti
- Memoria, moodlet nel manager
- Lifecycle, ageing, morte, gravidanza
- Identità, sessualità, cultura
- Vizi, dipendenze, background
- Riflessione, crisi, narrazione
- `LifecycleManager`
- Multi-threading, batch DB, `flush` differito
- Cambio di `save`/`load`: `NPCState` è in-memory, ricostruito da DB

## Criteri di accettazione

1. **248 test esistenti restano verdi, invariati.** Nessuna modifica
   ai test esistenti. Se un test va toccato, il refactor ha cambiato
   comportamento e va giustificato.

2. **Contract del manager in `run_tick`**: `run_tick` usa il manager
   iniettato (`npc_manager=`) se presente, altrimenti `NPCManager()`.
   `include_player` è propagato. Test in `test_tick_with_fake_manager.py`.
   - b. **Equivalenza col vecchio loop inline**: non più testabile
     direttamente dopo il refactor (il loop inline sparisce). Sostituito
     dal criterio #5 (10y identico), che è più forte perché misura
     87600 tick, non 20 seed.

3. **Determinismo**: `run_tick` con `NPCManager` produce stessa
   sequenza di `TickDecision` per 50 tick consecutivi, stesso seed,
   stesso DB. Test cross-DB (già coperto da `test_tick.py` esistente,
   verificare che passi).

4. **Ordine**: `update_all` itera in ordine di `character_id`
   crescente, indipendentemente dall'ordine di `states` in input.
   Test: `test_update_all_sorted_by_character_id`.

5. **10y identico a 1.4.0**: `10y-1.5.0.json` deve avere gli stessi
   numeri di `10y-1.4.0.json` per `mood_mean`, `balance_mean`,
   `purchase_transactions`, `salary_transactions`,
   `job_attendance_rate`. Se differisce, c'è un bug di equivalenza.
   **Questo è l'oracolo principale del refactor.**

6. **Query per tick non aumentano**: contatore SQLAlchemy
   (`event.listens_for(engine, "before_cursor_execute")`)
   prima/dopo il refactor, su 100 tick. Se il numero di query cresce,
   va motivato o corretto.
   **NON IMPLEMENTATO in B1+B2, poi risolto**: `load` fa N+1 (una
   query per personaggio per `needs_of`). Su 4 NPC è ~4 query in più
   per tick rispetto al loop inline. La stima originale "irrilevante
   (< 1ms)" era sbagliata: misurato su 10y, costa ~11 secondi (0.9%
   del totale). Non era la causa del −7.7% di 1.5.0: il baseline
   `76.5 tps` di 1.4.0 non era valido (macchina più scarica).
   Rimisurato 1.4.0 lo stesso giorno di 1.5.1: `72.3 tps`. La
   differenza reale è **2.2%**, non 7.7%. Corretto in 1.6.0 con
   `needs_of_many`: guadagno misurato +0.9% (70.6 → 71.3).

7. **`NPCManagerLike` usabile in test**: un finto manager che ritorna
   `TickDecision` fisse produce lo stesso `TickReport` (a meno dei
   campi derivati da DB). Test:
   `test_run_tick_uses_injected_manager`,
   `test_run_tick_passes_include_player_to_manager`.

8. **Test**: 248 + ≥ 13 nuovi = **≥ 261 verdi**.
