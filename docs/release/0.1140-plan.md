## Motivazione

FASE 3.6a-c del TODO: `npc/skills/`, training actions, migrazione
`5200_08`. Oggi il salario è fisso: Luca prende 25/giorno per sempre,
qualunque cosa faccia. Le skill rendono il lavoro significativo e

## Design

### `SkillKind`

```python
class SkillKind(StrEnum):
    BARISTA = "barista"
    INSEGNANTE = "insegnante"
    COMMESSO = "commesso"
    STUDENTE = "studente"
```

Separato da `JobTitle` (stessi valori, oggi). La separazione permette
di aggiungere skill senza job (es. `COOKING`, `PAINTING` in 0.1150+)
e job senza skill (nessuno oggi, ma il modello lo permette).

### `Skill` model

```python
class Skill(Base):
    __tablename__ = "skills"
    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    character_id: Mapped[int] = mapped_column(
        ForeignKey("characters.id", ondelete="CASCADE"), nullable=False
    )
    kind: Mapped[SkillKind] = mapped_column(SAEnum(SkillKind, native_enum=False), nullable=False)
    level: Mapped[float] = mapped_column(Float, nullable=False, default=0.0)
    __table_args__ = (
        UniqueConstraint("character_id", "kind", name="uq_skills_character_kind"),
        CheckConstraint("level >= 0.0 AND level <= 100.0", name="ck_skills_level"),
    )
```

### Formula salario

```python
def wage_with_skill(daily_wage: float, skill_level: float) -> float:
    """Salario modulato dalla skill. +50% a livello 100."""
    return float(daily_wage * (1.0 + max(0.0, min(100.0, skill_level)) / 200.0))
```

| Livello | Moltiplicatore |
| --- | --- |
| 0 | 1.00 |
| 20 | 1.10 |
| 50 | 1.25 |
| 100 | 1.50 |

Salario base (job.daily_wage) è il **minimo**: chi ha skill 0 prende
il base. Chi ha skill 100 prende +50%. Non c'è penalità per skill
basse (vedi §Rischi).

## Rischi

- (a) **`purchase_transactions` cambia**: se succede, qualcosa legge
  `balance` in utility (`score`) che non ho visto. Da indagare.
- (b) **`balance_min` di luca/giulia**: sale, è atteso. Ma se
  `balance_min = 0` (luca/giulia avevano min 100), allora i soldi
  extra vengono spesi, e `purchase` sale. Se succede, `purchase`
  non è invariato → contraddice (a). Da indagare se accade.
- (c) **`CheckConstraint` su SQLite**: `CHECK (level >= 0 AND level
  <= 100)` è enforced da SQLite nativamente (non è una FK). Test
  esplicito.
- (d) **`Skill` senza training**: le skill sono statiche. Se in
  0.1150 aggiungiamo training, il 10y cambia (skill salgono, salari
  salgono). Documentato.
- (e) **`SkillKind` 1:1 con `JobTitle`**: se un giorno un NPC
  cambia lavoro (non oggi), la skill resta. Va gestito in 0.1150+
  (`JobService.assign`).
